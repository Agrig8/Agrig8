# Agrig8 Issues #112-115: Infrastructure Improvements

## Issues Overview

### Issue #112: Add Terraform plan artifact retention
**Summary**: Attach sanitized Terraform plans to workflow runs and document review expectations.

**Primary Area**: `.github/workflows/terraform.yml`

**Current State**: The Terraform workflow validates and lints but doesn't retain plans for review.

**Proposed Changes**:
1. Add a `terraform plan` step to the workflow for each environment
2. Sanitize sensitive values from plan output
3. Upload plans as workflow artifacts
4. Document review expectations in workflow comments or docs

**Implementation Notes**:
- Use `terraform plan -out=tfplan` to generate binary plan
- Use `terraform show -json tfplan` to convert to reviewable JSON
- Sanitize secrets/credentials before upload
- Set artifact retention policy (e.g., 30 days)
- Add step for each environment (dev, staging)

**Files to Modify**:
- `.github/workflows/terraform.yml`
- Possibly add `docs/terraform-plan-review.md`

### Issue #113: Separate monitoring network ingress
**Summary**: Review monitoring ingress rules and preserve least-privilege access for observability services.

**Primary Area**: `infra/k8s/`

**Current State**: 
- Existing network policy: `backend-metrics-scrape-network-policy.yaml`
- Allows Prometheus to scrape backend metrics on port 9464
- Policy is in `default` namespace, should likely be in `innov8` namespace

**Proposed Changes**:
1. Review all monitoring ingress rules (Prometheus, Grafana)
2. Ensure monitoring services have dedicated network policies
3. Separate monitoring network ingress from application traffic
4. Apply least-privilege principle (only necessary ports/sources)
5. Document monitoring access patterns

**Current Network Policies**:
- `backend-metrics-scrape-network-policy.yaml` - Prometheus → Backend metrics
- Need to review: Grafana access, AlertManager, other observability tools

**Files to Review/Modify**:
- `infra/k8s/backend-metrics-scrape-network-policy.yaml`
- `infra/grafana/` directory
- `infra/prometheus/` directory
- Possibly add `infra/k8s/monitoring-network-policy.yaml`
- Update `docs/admin-network-isolation.md` or similar

### Issue #114: Add database backup restore drill
**Summary**: Automate or document a staged restore drill with integrity and recovery-time checks.

**Primary Area**: `infra` and `docs`

**Current State**:
- Automated backup cronjobs exist: `infra/k8s/cronjob-backup.yaml`
- Daily, weekly, monthly backup schedules configured
- Backups are encrypted and stored in S3
- **No documented restore procedure or drill**

**Proposed Changes**:
1. Create restore drill script/runbook
2. Document staged restore procedure:
   - Retrieve backup from S3
   - Decrypt backup
   - Restore to test environment
   - Verify data integrity
   - Measure recovery time
3. Automate periodic restore drills (quarterly recommended)
4. Document success criteria and recovery time objectives (RTO)

**Implementation Approach**:
- Create `scripts/db-restore-drill.sh`
- Create `docs/runbooks/database-restore-drill.md`
- Add GitHub Actions workflow for quarterly automated drill
- Include integrity checks (row counts, checksums, critical data validation)

**Files to Create**:
- `scripts/db-restore-drill.sh`
- `docs/runbooks/database-restore-drill.md`
- `.github/workflows/db-restore-drill.yml` (optional automation)

### Issue #115: Add container resource limits
**Summary**: Set CPU and memory limits for local and deployed services with documented sizing assumptions.

**Primary Area**: `docker-compose.yml` and `infra/k8s/`

**Current State**:
- **docker-compose.yml**: No resource limits on postgres, redis, or staging services
- **K8s manifests**: Some have limits (e.g., backup cronjobs), need to review all deployments

**Proposed Changes**:

#### docker-compose.yml
Add resource limits for all services:
- `postgres`: Set memory limits based on local dev needs (e.g., 512Mi-1Gi)
- `redis`: Set memory limits (e.g., 128Mi-256Mi)
- `postgres-staging`: Production-like limits (e.g., 1Gi-2Gi memory)
- `redis-staging`: Production-like limits (e.g., 256Mi-512Mi)
- Document sizing assumptions in comments

#### Kubernetes Manifests
Review and set resource requests/limits for:
- `backend-deployment.yaml`
- `frontend-deployment.yaml`
- `postgres-statefulset.yaml`
- `redis-deployment.yaml`

**Resource Sizing Assumptions to Document**:
- Database: typical workload size, concurrent connections
- Redis: cache size, eviction policy
- Backend: request rate, computation requirements
- Frontend: static serving requirements

**Files to Modify**:
- `docker-compose.yml`
- `infra/k8s/backend-deployment.yaml`
- `infra/k8s/frontend-deployment.yaml`
- `infra/k8s/postgres-statefulset.yaml`
- `infra/k8s/redis-deployment.yaml`
- Create or update `docs/resource-sizing.md`
